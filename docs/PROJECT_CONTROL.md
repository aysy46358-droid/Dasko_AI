# سجل حالة المشروع وأولوياته

هذا هو سجل القرار والمتابعة للمشروع على `experimental-work`. لا يعتمد على ذاكرة المحادثة وحدها. كل حالة يجب أن تتضمن دليلاً قابلاً للمراجعة. لا تعني كلمة «منجز» ضماناً مطلقاً؛ تعني أن الفحص المذكور نجح ضمن نطاقه.

## طريقة تسجيل الحالة

استخدم إحدى الحالات التالية فقط:

- **منجز بدليل:** يوجد ملف أو اختبار أو تشغيل CI يثبت النتيجة.
- **مفتوح:** لم يُنفذ أو بقيت خطوة واضحة.
- **متعذر التحقق:** يتطلب صلاحية أو بيئة غير متاحة؛ لا يُعامل كمنجز.
- **غير منطبق حالياً:** لا يستخدمه التطبيق في الوضع الحالي؛ يُعاد تقييمه قبل إدخال تلك الخدمة.

عند إغلاق بند، اكتب الدليل: الالتزام، الأمر/الاختبار أو رابط CI، وما الذي لم يثبته الفحص. حدّث هذا السجل في التغيير نفسه الذي يغلق البند. لا تكتب «الأمان مكتمل» أو «جاهز للإنتاج» من دون تحديد نطاق الفحوص.

## الحالة المؤكدة

- **البنية الأساسية — منجز بدليل محدود:** توجد طبقات `app`, `core`, `domain`, `features`, و`services`. عقد `AiEngine` في Domain، و`SendMessage` يستخدم العقد، و`lib/app/providers.dart` يربط التنفيذ الحالي `MockAiEngine`. راجع `PROJECT_MAP.md` والملفات المشار إليها هناك.
- **الاختبارات وسير البناء — منجز على الالتزام المذكور:** Workflow `Build APK` يشترط `dart format --set-exit-if-changed` و`flutter analyze` و`flutter test`، إضافة إلى فحوص الأصول والشبكة والتوقيع وبناء APK. النجاح يثبت نجاح هذه الخطوات على ذلك الالتزام، ولا يثبت سيناريوهات لم تغطها الاختبارات أو تجربة جميع الأجهزة.
- **الخريطة — منجز بدليل على `e4779af`:** `docs/PROJECT_MAP.md` يحتوي شرحاً معمارياً راجعته مع الملفات وجرداً مولّداً من فهرس Git بواسطة `tooling/project_map.py`. نجحت اختبارات المولّد الخمسة، وفحص القائمة الحالية، واختبار كشف القائمة القديمة محلياً. نجح فحص GitHub المستقل [Project map consistency](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42007967721)، ونجح [Build APK](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42007967629) على الالتزام نفسه. الـworkflow يملك صلاحية قراءة فقط، ولا يعتمد عليه بناء APK ولا يكتب إلى Git. لم يكن فحص الخريطة شرط دمج في ذلك الالتزام؛ حالة الفروع تحققت لاحقاً كما هو موثق أدناه.
- **حماية GitHub وسير PR — متحققان عبر GitHub API في 2026-11-08:** `main` يشترط PR وفحص الحالة الصارم `Flutter quality checks`، ويمنع الدفع القسري والحذف؛ عدد الموافقات المطلوبة صفر. `experimental-work` لا يشترط PR أو فحوص دمج، لكنه يمنع الدفع القسري والحذف. فرض الحماية على المشرفين مفعّل للفرعين. سير PR `pr_validation.yml` موجود على `main`، وشرط الحالة المطلوب مفعل.
- **إعدادات Actions الأخرى — مفتوحة جزئياً:** القراءة المؤرخة في 2026-11-07 أظهرت السماح بكل الإجراءات (`allowed_actions=all`) وعدم فرض تثبيت الإجراءات ببصمة SHA (`sha_pinning_required=false`)؛ لم يُعَد فحصهما في 2026-11-08. تعذرت قراءة أسماء أسرار Actions بسبب `403 Resource not accessible by integration`؛ لم تُقرأ قيم أسرار. يجب مراجعة ذلك منفصلاً دون تعطيل سير بناء APK.
- **ترقيم APK — إصلاح متحقق محلياً وبـCI:** اختبار التنافس كشف أن `git push` العادي يعيد نجاحاً مع `Everything up-to-date` إذا أنشأت عملية أخرى الوسم نفسه على الالتزام نفسه؛ وكان يمكن للعمليتين حينها تسجيل `versionCode` واحد. عُدّل `tooling/allocate_android_version.sh` ليعدّ الحجز ناجحاً فقط عندما يثبت `git push --porcelain` إنشاء وسم جديد، ويعيد المحاولة عند وجود الوسم مسبقاً. `tooling/test_allocate_android_version.sh` يختبر الحجز المتتابع والمتزامن بحاجز يفرض التصادم ورفض نسخة معطوبة على bare repositories مؤقتة. نجحت الاختبارات محلياً، ثم في وظيفة CI «Test Android build tooling» في [Build APK #129](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42369757643) على `6aad179`. حُجز `dasko-version-code-42` للبناء؛ واكتمل إنشاء APK والتحقق من توقيعه ورفعه بنجاح.
- **بيئة Android SDK — فحص runner متحقق، وفحص جهاز المستخدم مفتوح:** Flutter `3.47.8` يحدد `compileSdkVersion=36`، وGradle يأخذ `compileSdk` و`ndkVersion` من Flutter. تحقّق `setup_environment.sh` وCI من منصة `android-36` ووجود أداتي `aapt` و`apksigner`. اختبارات `tooling/test_setup_environment.sh` تغطي إعداداً صحيحاً، وغياب المنصة أو الأدوات، ورفض Java غير المطابق؛ وقد نجحت محلياً وعلى CI. كما نجح فحص المكونات الفعلية وإعدادات Android في Build APK #129. لكن في هذا الساندبوكس كان Java `21`، و`ANDROID_HOME`/`ANDROID_SDK_ROOT` غير مضبوطين، ووجدنا مجلداً جزئياً تحت `/usr/lib/android-sdk` لكن `flutter doctor` لم يتعرف إلى SDK صالح؛ لذلك لا يثبت هذا الفحص إعداد جهاز المستخدم أو البناء محلياً. تنبيه GitHub عن انتقال تسمية `ubuntu-latest` إلى Ubuntu 26 ظهر أثناء البناء، لكن البناء نجح؛ لا يزال اختيار نظام runner ثابت بند تحسين مستقل.
- **المحرك الحقيقي — مفتوح:** الرد الحالي من `MockAiEngine`؛ لا يوجد مزود LLM حقيقي موصول.
- **تنظيف الاعتمادات وتهيئة Crashlytics Dart — منجز بدليل محلي وCI:** أزيلت الاعتمادات المباشرة `flutter_secure_storage`, `shared_preferences`, `logger`, `intl`, `riverpod_annotation`, `riverpod_generator`, `json_serializable`, `build_runner`, و`json_annotation`. بقي `json_annotation` إصدار `4.9.0` اعتماداً انتقالياً في `pubspec.lock`، لذلك لم يُحذف يدوياً. أضيف `firebase_crashlytics: ^5.4.1`. نجح `flutter pub get --enforce-lockfile` و`dart format` و`flutter analyze` و15 اختباراً محلياً. نجح [Build APK #132](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42460503731) على `a63c0c7`، بما فيه التحليل والاختبارات وبناء APK والتحقق من توقيعه ورفعه؛ كما نجح [Format Dart #46](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42460503717) و[Project map consistency #6](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42460503729). لا تثبت هذه النتائج وصول تقارير Crashlytics إلى Console.

## الأولويات المفتوحة

### 1. بقية إعدادات GitHub الخارجية — مفتوحة بعد تفعيل حماية الفروع

حماية `main` و`experimental-work` وفحص PR المطلوب على `main` موثقة في «الحالة المؤكدة». سير `Build APK` يعمل عند الدفع ويدويّاً ويحجز وسم إصدار بصلاحية كتابة؛ لذلك لا تشغّله على pull request. المتبقي مراجعة سياسة Actions وتثبيت الإجراءات ببصمات موثوقة، والتحقق من وجود الأسرار دون قراءة قيمها؛ كانت صلاحية API تمنع قراءة أسمائها في آخر فحص.

### 2. مراجعة Firebase Console — متعذر التحقق

الكود يهيئ Firebase Core اختيارياً، ويهيئ Crashlytics على Android وiOS وmacOS بعد نجاح Firebase Core. لا يحتوي حالياً على تكامل Auth/قاعدة بيانات/Storage/Functions/App Check. قواعد Firebase والإنفاذ وإعدادات App Check في Console لم تُراجع هنا؛ لا تستنتج أنها آمنة أو غير آمنة. لا يُعد إعداد Crashlytics دليلاً على مراجعة هذه الإعدادات.

### 3. Crashlytics — تهيئة الكود منجزة؛ التحقق من الاستقبال مفتوح

في `lib/main.dart` تُرسل أخطاء Flutter غير القاتلة والأخطاء غير المتزامنة غير المعالجة إلى Crashlytics بعد استبدال الاستثناء الخام برسالة آمنة تتضمن نوع الخطأ ومصدراً ثابتاً فقط؛ تُرسل إطارات المكدس. لا تمرر الشيفرة نص الاستثناء أو تشخيصات Flutter أو محتوى المحادثة أو مفاتيح API أو معرّفات مستخدم. نجح CI، لكن لم يُختبر وصول تقرير إلى Firebase Console أو جهاز مستخدم؛ لم يُرسل اختبار crash ولم تُراجع إعدادات Firebase Console أو App Check.

### 4. تدقيق النصوص والقيم — مفتوح للتحقق النهائي

توجد ثوابت مركزية للنصوص والأصول، لكن هذا السجل لا يدّعي أن كل النصوص أو القيم ذات الدلالة في كل ملفات المشروع قد جُردت نهائياً. أعد المسح، وانقل ما له معنى أو تكرار أو قابلية ترجمة/تعديل؛ لا تحوّل كل رقم تصميمي صغير إلى ثابت بلا فائدة واضحة.

### 5. Gemini/محرك حقيقي — مؤجل إلى ما بعد تحديد الحدود الأمنية

لا تضع مفتاح Gemini داخل APK؛ قيم التطبيق الموزع يمكن استخراجها، لذلك يجب تحديد حد اعتماد على جهة خادمية أو تصميم آخر يحمي الاعتماد. قبل التنفيذ تحقق من الحصة المجانية والتكلفة والخصوصية الحالية، ثم اختبر النجاح والمهلة والفشل والحدود، مع عدم تسجيل الأسرار أو بيانات المستخدم الحساسة.

### 6. دمج إلى `main` — مؤجل

لا تدمج حتى تراجع الفرق الحالي بين الفرعين، وتتحقق من أي عيوب معروفة في `main`، وتنجح الفحوص المناسبة على نتيجة الدمج المقترحة. نجاح Build APK على التجريبي لا يثبت تلقائياً صحة الدمج أو سلامة `main`.

## قاعدة منع التشتت

- اعمل على بند واحد محدد في كل مرة، وعلى `experimental-work` فقط ما لم يُعتمد نطاق مختلف صراحةً.
- قبل التعديل: تحقق من الفرع والالتزام وحالة الشجرة، واقرأ الملفات التي سيتأثر بها التغيير.
- بعد التعديل: راجع الفرق، شغّل الاختبارات المرتبطة، ثم التحليل والبناء عندما ينطبق ذلك.
- عند فشل فحص: توقف وحدد هل الخلل في التطبيق أو الوثائق أو الأتمتة أو البيئة. لا تُخفِ الفشل ولا تتخطّه بصمت.
- لا تصف نتيجة بأنها مُتحقق منها إلا بذكر دليلها وحدوده.
