# سجل حالة المشروع وأولوياته

هذا هو سجل القرار والمتابعة للمشروع على `experimental-work`. لا يعتمد على ذاكرة المحادثة وحدها. كل حالة يجب أن تتضمن دليلاً قابلاً للمراجعة. لا تعني كلمة «منجز» ضماناً مطلقاً؛ تعني أن الفحص المذكور نجح ضمن نطاقه.

## طريقة تسجيل الحالة

استخدم إحدى الحالات التالية فقط:

- **منجز بدليل:** يوجد ملف أو اختبار أو تشغيل CI يثبت النتيجة.
- **مفتوح:** لم يُنفذ أو بقيت خطوة واضحة.
- **متعذر التحقق:** يتطلب صلاحية أو بيئة غير متاحة؛ لا يُعامل كمنجز.
- **غير منطبق حالياً:** لا يستخدمه التطبيق في الوضع الحالي؛ يُعاد تقييمه قبل إدخال تلك الخدمة.

عند إغلاق بند، اكتب الدليل: الالتزام، الأمر/الاختبار أو رابط CI، وما الذي لم يثبته الفحص. حدّث هذا السجل في التغيير نفسه الذي يغلق البند. لا تكتب «الأمان مكتمل» أو «جاهز للإنتاج» من دون تحديد نطاق الفحوص.

## الحالة المؤكدة

- **البنية الأساسية — منجز بدليل محدود:** توجد طبقات `app`, `core`, `domain`, `features`, و`services`. عقد `AiEngine` في Domain، و`SendMessage` يستخدم العقد، و`lib/app/providers.dart` يربط التنفيذ الحالي `MockAiEngine`. راجع `PROJECT_MAP.md` والملفات المشار إليها هناك.
- **الاختبارات وسير البناء — منجز على الالتزام المذكور:** Workflow `Build APK` يشترط `dart format --set-exit-if-changed` و`flutter analyze` و`flutter test`، إضافة إلى فحوص الأصول والشبكة والتوقيع وبناء APK. النجاح يثبت نجاح هذه الخطوات على ذلك الالتزام، ولا يثبت سيناريوهات لم تغطها الاختبارات أو تجربة جميع الأجهزة.
- **الخريطة — منجز بدليل على `e4779af`:** `docs/PROJECT_MAP.md` يحتوي شرحاً معمارياً راجعته مع الملفات وجرداً مولّداً من فهرس Git بواسطة `tooling/project_map.py`. نجحت اختبارات المولّد الخمسة، وفحص القائمة الحالية، واختبار كشف القائمة القديمة محلياً. نجح فحص GitHub المستقل [Project map consistency](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42007967721)، ونجح [Build APK](https://github.com/aysy46358-droid/Dasko_AI/actions/runs/42007967629) على الالتزام نفسه. الـworkflow يملك صلاحية قراءة فقط، ولا يعتمد عليه بناء APK ولا يكتب إلى Git. لم نضبطه كشرط دمج؛ حالة حماية الفروع الخارجية ما زالت غير متحققة.
- **فحص إعدادات GitHub — القراءة اكتملت، والمعالجة مفتوحة:** في 2026-11-07 أرجع GitHub `Branch not protected` لكل من `experimental-work` و`main`، ولم توجد Rulesets. إعداد Actions يسمح بكل الإجراءات (`allowed_actions=all`) ولا يشترط تثبيت الإجراءات ببصمة SHA (`sha_pinning_required=false`). الإعداد الافتراضي لصلاحية `GITHUB_TOKEN` هو القراءة فقط، مع صلاحيات أوسع محددة على مستوى الوظائف عند الحاجة، مثل كتابة وسم حجز الإصدار. تعذرت قراءة أسماء أسرار Actions بسبب `403 Resource not accessible by integration`؛ لم تُقرأ قيم أسرار. لا تغيّر هذه الإعدادات الخارجية قبل اختيار حماية لا تعطل سير الدفع الحالي أو البناء.
- **ترقيم APK — إصلاح واختبارات محلية؛ انتظار فحص CI:** اختبار التنافس كشف أن `git push` العادي يعيد نجاحاً مع `Everything up-to-date` إذا أنشأت عملية أخرى الوسم نفسه على الالتزام نفسه؛ وكان يمكن للعمليتين حينها تسجيل `versionCode` واحد. عُدّل `tooling/allocate_android_version.sh` لاعتبار الحجز ناجحاً فقط عندما يثبت `git push --porcelain` إنشاء وسم جديد، وإعادة المحاولة عند وجود الوسم مسبقاً. يختبر `tooling/test_allocate_android_version.sh` الحجز المتتابع والمتزامن ورفض نسخة معطوبة على bare repositories مؤقتة؛ وحاجز الاختبار يجعل العمليتين تقرآن الحالة السابقة نفسها، فيضمن اختبار مسار التصادم/retry. نجحت الاختبارات محلياً دون إنشاء أو تغيير وسوم في GitHub الحقيقي. أضيفت الاختبارات إلى وظيفة CI قراءة فقط قبل وظيفة حجز الوسم؛ يلزم نجاح CI على الالتزام الجديد لإغلاق التحقق البعيد.
- **بيئة Android SDK — قيود مثبتة واختبارات محلية؛ انتظار CI:** Flutter `3.47.8` يحدد `compileSdkVersion=36`، وGradle يأخذ `compileSdk` و`ndkVersion` من Flutter. تحقّق `setup_environment.sh` وCI الآن من منصة `android-36` ووجود أداتي `aapt` و`apksigner` قبل متابعة البناء. اختبار `tooling/test_setup_environment.sh` يستخدم أدوات وSDK وهمية لاختبار الحالة الصحيحة، وغياب المنصة أو الأدوات، ورفض Java غير المطابق؛ وقد نجح محلياً. في هذا الساندبوكس كان Java `21`، و`ANDROID_HOME`/`ANDROID_SDK_ROOT` غير مضبوطين، ووجدنا مجلداً جزئياً تحت `/usr/lib/android-sdk` لكن `flutter doctor` لم يتعرف إلى SDK صالح؛ لذلك لم يثبت هذا الفحص إعداد جهاز المستخدم أو بناء Android محلياً. نجاح CI يثبت البناء على runner فقط.
- **المحرك الحقيقي — مفتوح:** الرد الحالي من `MockAiEngine`؛ لا يوجد مزود LLM حقيقي موصول.

## الأولويات المفتوحة

### 1. معالجة إعدادات GitHub الخارجية — مفتوح بعد فحص القراءة

نتيجة القراءة موثقة في «الحالة المؤكدة». يلزم تصميم تحقق PR آمن قبل فرض فحوص دمج إلزامية؛ سير APK الحالي يحجز version tag بصلاحية كتابة، لذلك لا ينبغي تشغيله كما هو على pull request. يلزم أيضاً مراجعة نطاق Actions المسموح بها وتثبيتها ببصمات موثوقة قبل تفعيل شرط SHA. أسرار Actions غير متحققة بسبب حدود صلاحية API.

### 2. مراجعة Firebase Console — متعذر التحقق

الكود يهيئ Firebase Core اختيارياً، ولا يحتوي حالياً على تكامل Auth/قاعدة بيانات/Storage/Functions/App Check/Crashlytics بحسب README والاعتمادات. قواعد Firebase والإنفاذ وإعدادات App Check في Console لم تُراجع هنا؛ لا تستنتج أنها آمنة أو غير آمنة. راجعها قبل إدخال أي ميزة تعتمد على خدمة Firebase.

### 3. سياسة الرصد ومعالجة أخطاء الإنتاج — مفتوح

لا يوجد حالياً تكامل Crashlytics أو خدمة رصد مفعّلة بحسب README. قبل الاختيار، حدد البيانات المسموح تسجيلها، والاستثناءات التي تُرفع، ومنع تضمين مفاتيح API أو محتوى المحادثة أو بيانات شخصية حساسة. اختر حلاً بعد التحقق من التكلفة والخصوصية والحدود الحالية.

### 4. تدقيق النصوص والقيم — مفتوح للتحقق النهائي

توجد ثوابت مركزية للنصوص والأصول، لكن هذا السجل لا يدّعي أن كل النصوص أو القيم ذات الدلالة في كل ملفات المشروع قد جُردت نهائياً. أعد المسح، وانقل ما له معنى أو تكرار أو قابلية ترجمة/تعديل؛ لا تحوّل كل رقم تصميمي صغير إلى ثابت بلا فائدة واضحة.

### 5. Gemini/محرك حقيقي — مؤجل إلى ما بعد تحديد الحدود الأمنية

لا تضع مفتاح Gemini داخل APK؛ قيم التطبيق الموزع يمكن استخراجها، لذلك يجب تحديد حد اعتماد على جهة خادمية أو تصميم آخر يحمي الاعتماد. قبل التنفيذ تحقق من الحصة المجانية والتكلفة والخصوصية الحالية، ثم اختبر النجاح والمهلة والفشل والحدود، مع عدم تسجيل الأسرار أو بيانات المستخدم الحساسة.

### 6. دمج إلى `main` — مؤجل

لا تدمج حتى تراجع الفرق الحالي بين الفرعين، وتتحقق من أي عيوب معروفة في `main`، وتنجح الفحوص المناسبة على نتيجة الدمج المقترحة. نجاح Build APK على التجريبي لا يثبت تلقائياً صحة الدمج أو سلامة `main`.

## قاعدة منع التشتت

- اعمل على بند واحد محدد في كل مرة، وعلى `experimental-work` فقط ما لم يُعتمد نطاق مختلف صراحةً.
- قبل التعديل: تحقق من الفرع والالتزام وحالة الشجرة، واقرأ الملفات التي سيتأثر بها التغيير.
- بعد التعديل: راجع الفرق، شغّل الاختبارات المرتبطة، ثم التحليل والبناء عندما ينطبق ذلك.
- عند فشل فحص: توقف وحدد هل الخلل في التطبيق أو الوثائق أو الأتمتة أو البيئة. لا تُخفِ الفشل ولا تتخطّه بصمت.
- لا تصف نتيجة بأنها مُتحقق منها إلا بذكر دليلها وحدوده.
